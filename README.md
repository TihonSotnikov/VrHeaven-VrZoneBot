# VR Heaven — бот учёта VR-сеансов

Телеграм-бот, в котором администратор ПК-клуба оформляет оплаченный
VR-сеанс, а бот считает, кто кому сколько должен: вознаграждение
администратора, долю владельца клуба и остаток VR Heaven.

Что бот обязан делать — в [SPEC.md](SPEC.md). Как его держать в
работе — в [deploy/RUNBOOK.md](deploy/RUNBOOK.md). Здесь — устройство кода.

### Три решения, вокруг которых собрано остальное

**Запись возможна только в транзакции.** Изменяющие методы `db` требуют
`tx`, а получить его можно единственным способом:

```python
async with db.write() as tx:            # BEGIN IMMEDIATE под общим локом
    order, created = await db.create_order(tx, ...)
    await db.audit(tx, actor, "order.create", "order", order["id"], ...)
    await notify.to_user(db, tx, owner, text, kind="order_owner", dedup=...)
# COMMIT здесь; исключение — ROLLBACK, ничего частичного
```

Заказ, запись в журнал действий и уведомления коммитятся вместе. Место в
лесенке считается внутри той же транзакции, поэтому два устройства одного
кабинета получают ступени 1 и 2. Повтор формы отсекается уникальным
`client_token`, а не удачным стечением обстоятельств.

**В чате одно Окно и сколько угодно Записей.** Кнопки есть ровно у одного
сообщения — Окна; всё остальное (чеки, уведомления, отчёты, копии,
выгрузки) остаётся навсегда. Появилась Запись — Окно переставляется под неё
вместе с содержимым и кнопками, поэтому экран оплаты не теряется. Новое
Окно отправляется **до** удаления прежнего. Бот удаляет ровно две вещи:
своё Окно и сообщение пользователя.

**Текст собирается так, что сломать его нечем.** Шаблон пишем мы, значения
экранируются функцией `h()`; забыть экранировать нечего — другого способа
подставить значение нет. Длина ограничивается до отправки, по границе тега.

## Запуск для разработки

Нужен [uv](https://docs.astral.sh/uv/) и Python 3.12.

```bash
uv sync
cp .env.example .env      # свой тестовый бот, не боевой
uv run main.py
```

**Отдельный бот для разработки обязателен.** Telegram отдаёт апдейты одному
потребителю: запуск с боевым токеном уводит их у сервера.

## Тесты

```bash
uv run pytest -q
```

Тесты проверяют не только логику, но и контракт Telegram: каждая отправка
разбирается на теги, длину и клавиатуру, поэтому сообщение, которое
Telegram отверг бы, роняет тест в месте отправки. Одновременные действия
проверяются настоящим `Dispatcher` с настоящим хранилищем состояния, а не
его моделью.

Проверка деловых инвариантов запускается и отдельно, над любым файлом базы:

```bash
uv run python invariants.py /путь/к/adminbot.db
```

## Настройки окружения

| Переменная | Смысл | По умолчанию |
|---|---|---|
| `BOT_TOKEN` | токен бота | — (обязательна) |
| `BOT_TOKEN_FILE` | файл с токеном вместо переменной | — |
| `ADMIN_IDS` | Telegram ID супер-админов через запятую | — (обязательна) |
| `TIMEZONE` | часовой пояс расписаний | `Europe/Moscow` |
| `DB_PATH` | файл базы | `adminbot.db` |
| `DATA_DIR` | каталог данных (блокировка, копии) | каталог базы |
| `BACKUP_DIR` | каталог копий | `DATA_DIR/backups` |
| `BACKUP_KEEP_DAYS` / `_WEEKS` / `_MONTHS` | ротация копий | 7 / 8 / 12 |
| `BACKUP_OFFHOST_CMD` | команда выгрузки копии, `{path}` и `{name}` | не задана |
| `LOG_JSON`, `LOG_LEVEL` | журналирование | `false`, `INFO` |

На сервере токен приходит через `LoadCredential` systemd и в окружении
процесса не появляется.

## Данные

Один файл SQLite в режиме WAL. Схема версионируется `PRAGMA user_version`;
миграции атомарны, с пост-условиями и неизменяемой копией перед началом.
База новее программы — отказ старта: откат релиза поверх новой схемы
должен быть громким.

Таблицы: `users`, `user_chats`, `orders`, `promos`, `bonuses`, `payouts`,
`settings`, `super_admins`, `audit_log`, `outbox`, `chat_windows`,
`fsm_state`.
